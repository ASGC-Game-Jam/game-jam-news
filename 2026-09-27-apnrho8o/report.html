I'm sure there are ways to work around this constraint. One really good way I find is sprinkling self-talk expressions --- a lot of things we'd say to ourselves in the heat of the moment. So any spontaneous reaction in the form of frustration, surprise, sadness, exhilaration/elation, etc I feel could be great to insert some words. A word here, a phrase there. It's a reflection of how our brains are wired to think in the language we're comfortable in. I cuss and think in English, but peeps I know with whom I share languages will have quite a different reaction to the same situations I face in context to the languages they speak. That's one of the ways I'm able to identify where they may originally come from, and what degree of English I should keep to so that our comms link isn't lost.

AC2 does something similar. While largely having English lines with some Italian lines, the game uses Italian words particularly when a character is shown to have a spontaneous reaction to something. Really good way to 1) repeat the words, 2) not have to worry about what the player understands (because they see how its associated with the scene, and the character's following action), and 3) arguably, make for a more believable society with just the 20% of the work one puts into it.

The big trick is to focus on 3 main things when you're doing your concepts. 1. Visual Clarity 2. Recognizable Silhouette 3. "Model-ability"

You want to make sure the intent of your designs are clear to the viewer. Confusion causes frustration and frustration tends to be a bad thing When in doubt, use reference. If you're unsure ask someone next to you what they think it is, if they guess wrong, then you've got some more work to do.

Once you've got clear ideas, make sure they can be read from afar. This is helpful in games when the player needs to know what they're looking at in a split second. Is it friend or foe? dangerous or safe? It's important for the player to know.

Finally, and most importantly, can the 3D modelers model it? You want to make sure your image is clear enough for someone to take into 3D and build what you had in mind with minimal questions

In a code review thread, Clara defended a deliberately repetitive MetaSounds audio parameter interface template against the suggestion that its TODOs and duplication should be replaced with an abstract class or structural inheritance. She gave two reasons. First, Unreal's IAudioParameterInterfaceRegistry expects unique, static FMetasoundFrontendVersion layouts compiled at startup and relies on preprocessor macros like AUDIO_PARAMETER_INTERFACE_MEMBER_DEFINE, which bypass the C++ virtual table, so virtual methods and abstract parents won't carry safely to the async audio threads. Second, the code is meant as a hands-on learning template for the tech audio team, and an automated abstract wrapper would turn it into a "black box." She committed to adding Markdown documentation explaining the engine context and to tightening up the comments.

Carlos Ortiz accepted the reasoning, noting he would push back more if this weren't an educational game jam. He asked that the docs also describe what a polymorphic approach might look like, so people can peek inside those black boxes. Clara agreed to write up something on larger templating and said she would probably reference the Harmonix plugin as a good example.

The TODOs and duplication definitely make this look like pure boilerplate that should be replaced with an abstract class or structural inheritance.

I don't want to try and use abstract classes or polymorphism here, due to the nature of MetaSounds and how UE handles them. It is meant to act as a template for the tech audio team, showing how a single interface is created so they can use it themselves on their own projects.

Unreal Registry Constraints: Unreal's IAudioParameterInterfaceRegistry expects unique, static FMetasoundFrontendVersion layouts compiled at startup. Because it relies heavily on preprocessor macro magic (like AUDIO_PARAMETER_INTERFACE_MEMBER_DEFINE), it completely bypasses the standard C++ runtime virtual table. Virtual methods and abstract parent classes won't cross over safely to the async audio threads.

Educational Value: The goal of this specific code is to serve as a hands-on learning template for the rest of the developers. By forcing them to copy this basic layout and manually define their own namespaces, pins, and data types, they will actually learn how Unreal’s sound interfaces lock into game code. If we hide this behind a complex, automated abstract wrapper, it becomes a "black box" and nobody learns how the engine actually works.
